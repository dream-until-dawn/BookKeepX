# 账单导入设计（P1-6）

- 依据：[ADR-0003 解析模板](./adr/0003-import-templates.md)、[ADR-0004 分类与规则](./adr/0004-categories-and-rules.md)、P0-1 ~ P0-1e 探针结论、[数据模型](./data-model.md)
- 范围：内置模板（微信 xlsx、支付宝 csv、招行 PDF）的上传 → 识别 → 解析 → 自校验 → 退款关联 → 去重 → 自动分类 → 预览 → 提交 → 整批撤销；导入页面
- 不在本步：用户自定义模板向导（P1-7）、用户规则管理与"从修改中学习"（P1-8）

## 1. 模块划分（对架构的一处调整）

架构文档原计划把导入引擎放在 `packages/core`。实现时发现引擎依赖 exceljs、pdfjs-dist 等体积很大的库，而 `core` 同时被前端引用，放在一起会拖大前端包。因此：

| 包 | 内容 | 谁用 |
|---|---|---|
| `packages/core` | 金额、时区、预置分类、**分类规则引擎**（纯函数，无重依赖） | 前端 + 服务端 |
| `packages/importers`（新增） | 文件读取、通用解析引擎、内置模板、自校验、退款关联 | 仅服务端 |

## 2. 流程

```
上传文件（≤10 MB）
  ① 按文件头识别类型（xlsx / pdf / csv），不信任扩展名
  ② 自动识别模板（ADR-0003 打分）
       高置信 → 继续；有候选但不确定 → 返回候选让用户选，用户选定后重新提交
       无候选 → 提示暂不支持（P1-7 起可自定义模板）
  ③ 解析 + 自校验（汇总比对 / 余额链）→ 不通过则拒绝导入，并列出问题
  ④ 文件内退款关联（P0-1e）
  ⑤ 与账本已有数据比对：
       同来源重复：平台单号已存在 / 银行去重键已存在 → 标记"已导入过"，默认不导入
       退款的原消费在以前的导入里：按单号前缀在库中查找（支付宝）
       跨来源重复（ADR-0004 Q2-B）：见 §4
  ⑥ 自动分类：用户规则 > 系统规则 > 来源映射（ADR-0004 决策链）
  ⑦ 生成预览，存入 import_batches.preview（状态 previewing，24 小时后过期）
预览页：用户可以改分类、取消勾选某些行
  ⑧ 提交：一个数据库事务内写入全部流水、更新批次状态
整批撤销：删除该批次写入的全部流水（其他批次对它们的退款 / 重复引用先解除）
```

## 3. 接口

| 接口 | 说明 |
|---|---|
| `POST /api/ledgers/:ledgerId/imports` | 上传（multipart：`file`，可选 `templateId`、`accountId`）。结果三种之一：预览 `{ status: 'preview', batch }`；需要选择模板 `{ status: 'choose_template', candidates }`；校验失败 422 `IMPORT_VERIFY_FAILED` 带问题列表 |
| `GET /api/ledgers/:ledgerId/imports` | 导入历史 |
| `GET /api/ledgers/:ledgerId/imports/:batchId` | 批次详情（预览中的批次含预览行） |
| `POST /api/ledgers/:ledgerId/imports/:batchId/commit` | 提交：`{ overrides: [{ index, categoryId?, include? }] }` |
| `POST /api/ledgers/:ledgerId/imports/:batchId/revert` | 整批撤销 |
| `DELETE /api/ledgers/:ledgerId/imports/:batchId` | 放弃预览 |

**同一文件重复上传**（文件指纹相同，且之前已提交）：照常解析，但所有行都会被标记为"已导入过"，预览里一目了然。

## 4. 跨来源重复（ADR-0004 Q2-B）

同一笔消费既出现在平台账单（支付宝 / 微信，用银行卡付款），又出现在银行流水。判定条件：

- 同一天、同金额；
- 平台记录的支付方式里包含该银行卡的尾号（如"招商银行储蓄卡(1032)"），且银行记录属于尾号 1032 的账户。

处理：两条都保留，**银行那条**的 `duplicate_of_id` 指向平台那条，不计入统计。无论先导入哪一边都会在后导入时建立关联。

理财申购 / 转入零钱通这类（Q2-A）由分类规则识别为中性，不走重复关联。

## 5. 资金账户的对应

- 用户在上传时可以选择账户；
- 不选时自动推断：微信账单 → 唯一的"微信"类型账户；支付宝同理；银行流水 → 卡号后四位与文件中账号尾号一致的账户；推断不出时为空；预览页可补选账户，用同一文件重新识别（从导入历史继续的预览没有原文件，需重新上传）。

## 6. 预览行的状态

| 状态 | 含义 | 默认是否导入 |
|---|---|---|
| `new` | 新记录 | 是 |
| `duplicate` | 本账本已导入过（同单号 / 同去重键） | 否 |
| `skipped` | 账单中按规则跳过的（交易关闭无退款、0 元） | 否（只展示） |

另外带标记：`refund`（退款及其关联情况）、`crossSourceDuplicate`（跨来源重复，将导入但不计入统计）。

## 7. 安全

- 文件大小上限 10 MB，只接受 xlsx / pdf / csv（按文件头判断）；
- 不保存原始文件（data-model.md Q1），只存文件指纹和每行原始数据；
- 解析在服务端进行，模板中不含可执行代码、不含正则（ADR-0003）。

## 8. 待真实数据确认的问题

| # | 问题 | 当前处理 | 需要的样本 |
|---|---|---|---|
| 1 | **跨账单周期的退款**（上月买、本月退、导出本月账单）：支付宝的支出汇总是否扣除这笔退款？现有 5 份样本中所有退款的原消费都在同一文件内，无法验证 | 两种口径都接受（扣除 / 不扣除），两种都对不上才报错；原消费在本文件内的退款不享受"不扣除"口径，避免放松校验 | 一份包含"上月商品本月退款"的支付宝账单 |
| 2 | **用银行卡在支付宝 / 微信消费**（Q2-B）：现有样本中唯一一笔（9-24 车险）超出了招行流水的日期范围，端到端无法验证 | 以合成数据测试了两个方向（先银行后平台、先平台后银行） | 同一时间段的支付宝账单 + 银行流水，且其中有用该卡支付的消费 |

## 9. 自定义解析模板（P1-7）

内置模板不认识的文件（新银行、旧版导出格式），用户可以在页面上用**列映射向导**配置一份模板。保存后，下次上传同类文件会自动识别。

### 9.1 探针结论（2026-09-24，真实样本）

用"向导能生成的最小模板"（只含表头、列映射、金额方式、收支取值、时间格式，不含自校验和退款配置）解析旧版样本：

| 样本 | 份数 | 结果 |
|---|---|---|
| 旧版微信 csv | 24 | 全部解析，0 错误 |
| 旧版支付宝 csv（2021） | 1 | 时间写法为 `2021/12/31 8:54`（不补零、无秒），现有时间格式不支持 → 引擎新增两种宽松格式后 0 错误 |

发现的问题：用户模板通常没有标题关键词，按原打分公式最高 0.7 分，**永远不会被自动选中**；旧版支付宝文件上，内置模板（0.75）反而比用户模板分数高。→ 见 9.4。

实现后按向导的推荐逻辑用真实样本端到端验证（读取样本 → 推荐配置 → 试解析 → 保存 → 上传同类文件），又发现三个问题，均已修正：

| 发现 | 原因 | 修正 |
|---|---|---|
| 用一份旧版微信账单建的模板，另一位用户的 16 份账单全部被拒 | 向导只看前 200 行，建模板的文件里没有 `/`（中性交易），推荐的收支取值缺这一项 | 来源为微信 / 支付宝时，编译时补上平台标准取值（用户设置优先） |
| 旧版支付宝推荐的识别关键词是"共980笔记录" | 关键词取自说明文字第一行，而笔数每份文件不同，同类其他文件都会匹配不上 | 含数字的行不做关键词；改为推荐"支付宝（中国）网络技术有限公司  电子客户回单" |
| 旧版支付宝的"交易关闭"不会被跳过 | 唯一一条在第 955 条，向导样本看不到 | 来源为支付宝时默认跳过"交易关闭"，与内置模板一致 |

修正后：24 份旧版微信 csv、1 份旧版支付宝 csv 全部被自动识别并导入，再次上传全部识别为重复；已有用户模板时，新版文件仍由内置模板识别。

### 9.2 范围

- 支持 csv、xlsx；**PDF 暂不支持**自定义（PDF 的列靠文字坐标切分，需要可视化选区，放到以后）；
- 不支持在向导中配置汇总校验（格式五花八门，用户难以正确配置）；可选"余额连续性校验"；
- 模板属于**用户**（不属于账本），同一用户的所有账本都能用。

### 9.3 存储：保存向导配置，加载时编译为标准模板（对 ADR-0003 §4 的调整）

`import_templates.definition` 保存的是**向导配置**（下称 spec），不是完整模板 JSON。加载时由 `compileUserTemplate(spec)` 编译为标准模板，再经模板 schema 严格校验，之后与内置模板走同一套引擎。原因：

- 用户能配置的只是模板能力的一个小子集，存 spec 让可配置范围一目了然，也减少被构造恶意模板的可能；
- 编辑模板时向导能原样还原用户的选择；
- 引擎升级（例如更好的默认值）会自动作用到已保存的用户模板。

spec 内容：

| 字段 | 说明 |
|---|---|
| fileType | csv / xlsx |
| sourceKind | 账单来源：微信 / 支付宝 / 储蓄卡 / 信用卡 / 其他。选微信、支付宝时来源标识沿用 `wechat` / `alipay`，**与内置模板共用单号去重、来源分类映射、退款识别规则**（例如旧版微信 csv 与新版 xlsx 中的同一笔交易能被识别为重复）；其他来源的来源标识为 `u-<模板 id>` |
| header | 表头行的全部列名（作为识别用的必需列，越完整越不容易误认别的文件） |
| columns | 字段 → 列名：时间（必填）、金额 / 收入 / 支出、对方、说明、单号、支付方式、原分类、余额、状态 |
| amountMode | 带符号单列 / 金额 + 收支列 / 收入支出分两列 |
| directionMap | 收支列的取值 → 收入 / 支出 / 中性 |
| skipStatuses | 状态列中需要跳过的取值（如"交易关闭"） |
| timeFormat | 从样本自动推断，用户可改 |
| titleKeywords / fileNameKeywords | 识别用的关键词，向导从表头之前的说明文字中推荐 |
| balanceCheck | 余额连续性校验（映射了余额列时可选） |

### 9.4 识别打分的调整

- **没有配置标题关键词、且文件表头与模板表头完全一致**的模板，关键词这一项不参与打分，其余两项按比例放大：`(表头 × 0.4 + 试解析 × 0.3) / 0.7`。表头只是"包含"必需列时不放大（否则只要求"时间、金额"这类宽泛的模板会与内置模板打成平手，让正常的支付宝文件也要手动选模板——测试发现）。内置模板都有关键词，不受影响；
- 用户模板的必需列是**整行表头**，比内置模板更严格，降低误认别家文件的概率；
- 用户模板与内置模板一起参与打分，仍需"≥ 0.9 且领先 ≥ 0.2"才自动选用，否则让用户选。

### 9.5 去重

用户模板可能既没有单号列、也没有余额列，此时原有规则无法去重（再次上传会重复导入）。补充规则：去重键 = 账户 + 完整时间 + 带符号金额 + 对方 + **同一文件中完全相同记录的序号**。序号保证同一天两笔完全相同的交易（如两次 2 元地铁）不会被误判为重复，同一文件再次上传时序号不变、能正确识别为重复。有单号或余额的模板仍用原规则。

### 9.6 流程与接口

```
导入页上传 → 不支持 / 用户点"自定义模板"
  → 向导 ① 读取文件前 200 行（服务端，不保存文件）
         ② 点选表头行
         ③ 给各列选字段、选金额方式、填收支取值映射（从样本中自动收集取值）
         ④ 选账单来源、确认时间格式与识别关键词
         ⑤ 试解析：显示前 20 条解析结果、错误行、自校验结果、"下次能否自动识别"
         ⑥ 命名保存 → 用刚保存的模板继续导入（进入正常预览流程）
```

| 接口 | 说明 |
|---|---|
| `POST /api/import-templates/inspect` | multipart：`file`。返回文件类型与前 200 行单元格（文字）、推荐的表头行 |
| `POST /api/import-templates/test` | multipart：`spec`（JSON）+ `file`。试解析，不保存 |
| `GET /api/import-templates` | 我的模板列表 |
| `POST /api/import-templates` | 保存：`{ name, spec }`（保存前编译并校验） |
| `PATCH /api/import-templates/:id` | 修改名称 / spec；spec 变化时版本号 + 1 |
| `DELETE /api/import-templates/:id` | 删除；已导入的流水不受影响 |

上传接口的 `templateId` 可以是内置模板 id，也可以是自己的模板 id。批次记录模板 id 与版本；来源标识在生成预览时存入预览，提交时不再依赖模板（模板在预览期间被修改或删除也不影响提交）。
