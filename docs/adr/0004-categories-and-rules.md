# ADR-0004 统一分类体系与自动分类规则

- 状态：提议中（待确认）
- 日期：2026-09-24

## 背景

需求（负责人 2026-09-24）：各账单来源的分类名称不同、标准不一，由我们维护一套自己的分类；并允许用户自定义规则，例如"条目信息或备注里带'地铁'就归入交通"。

用真实样本统计了各来源的"原生分类"字段（P0-1c）：

| 来源 | 字段 | 性质 | 能否直接当分类 |
|---|---|---|---|
| 支付宝 | 交易分类（交通出行、餐饮美食、投资理财…） | 真正的消费分类，但较粗 | ✅ 可映射 |
| 微信 | 交易类型（扫二维码付款、商户消费、转账） | 支付形式 | ❌ 不能用，需要看对方 / 商品名 |
| 招商银行 | 交易摘要（快捷支付、银联代付、代发工资、账户结息…） | 大多是支付渠道，少数有语义 | ⚠️ 部分可用 |

结论：来源分类只能作为辅助信号，必须有自己的分类树 + 基于文本的规则。

## 决策

### 1. 系统预置分类树（我们维护）

- 两级分类，分三组：**支出**、**收入**、**中性**（中性 = 不计收支的资金流动，如理财申购、转到自己的账户、信用卡还款、充值提现）；
- 每个预置分类有一个稳定的英文键（如 `expense.transport.public`），与显示名解耦；
- 预置分类定义在代码仓库 `packages/core/categories/preset.json`，带版本号；
- 用户注册时**复制**一份到自己的 `categories` 表（记录 `preset_key`），之后用户可以改名、新增、隐藏、调整层级，不影响别人；
- 预置分类升级（例如新增"宠物"）时，通过 `preset_key` 判断哪些是新增的，提示用户是否加入，不强制覆盖。

### 2. 分类决策链（按优先级，命中即停）

```
① 手动指定        用户在预览或编辑时亲手选的分类，任何自动逻辑都不覆盖
② 用户规则        用户自己定义的规则，按用户设定的顺序逐条匹配
③ 系统关键词规则   我们内置的常识规则（如 对方/商品含"地铁""公交" → 交通·公共交通）
④ 来源分类映射    模板级映射：支付宝"餐饮美食" → 餐饮；招行"代发工资" → 工资
⑤ 未分类          留给用户处理（P3 由 agent 给建议）
```

每笔流水记录**分类来源** `category_source`（manual / user_rule / system_rule / source_hint / none）和命中的规则 id。界面可以显示"由规则『地铁 → 交通』归类"，让用户知道分类是怎么来的。

### 3. 规则结构（声明式、无正则）

```jsonc
{
  "name": "地铁归交通",
  "enabled": true,
  "priority": 10,                    // 数字小的先匹配
  "match": "all",                    // all：条件全部满足 | any：任一满足
  "conditions": [
    { "field": "anyText", "op": "containsAny", "values": ["地铁", "轨道交通"] },
    { "field": "direction", "op": "equals", "values": ["expense"] }
  ],
  "action": { "categoryKey": "expense.transport.public" }
}
```

- **字段**：`counterparty`（对方）、`description`（商品 / 摘要）、`note`（备注）、`paymentMethod`、`sourceHint`（来源原生分类）、`source`（来源模板 id）、`direction`、`amount`（分），以及 `anyText`（对方 + 商品 + 备注合并，对应"条目信息或备注里带某个词"这种最常见的写法）；
- **操作符**：文本类 `containsAny` / `notContains` / `equals` / `startsWith` / `endsWith`（忽略大小写和全角半角）；金额类 `gte` / `lte`；
- **动作**：设置分类；也可以把方向改成中性（例如"对方是我自己的名字 → 中性·转账"），让转给自己的钱不再算支出；
- **不支持正则**：理由同 ADR-0003（用户可编辑的内容不能成为 ReDoS 入口），而且关键词列表对普通用户更直观。

### 4. 规则的生命周期

- **从修改中学习**：用户在导入预览或流水列表里改了某笔的分类，弹出提示"以后『厦门地铁』都归到『交通·公共交通』？"，确认后自动生成一条用户规则（条件已预填）；
- **应用到历史**：新建或修改规则时可以选择"应用到已有流水"，只会改分类来源不是"手动指定"的记录；
- **冲突提示**：新规则保存前，用最近的流水试跑一遍，展示会影响哪些记录，以及和哪条已有规则冲突。

### 5. 数据表调整

| 表 | 变更 |
|---|---|
| `categories` | 新增 `preset_key`、`group`(expense/income/neutral)、`hidden` |
| `category_rules` | 改为：id, user_id, name, enabled, priority, match, conditions(jsonb), action(jsonb), hit_count, created_at |
| `source_hint_mappings` | 新增：user_id(可空 = 系统默认), source, hint, category_key —— 用户可以覆盖系统的来源映射 |
| `transactions` | 新增 `category_source`、`category_rule_id` |

### 6. 负责人已决事项（2026-09-24）

| # | 问题 | 决定 | 落地 |
|---|---|---|---|
| Q1 | 贷款 / 信用卡还款算支出还是中性？ | **算支出** | 预置分类新增 `expense.repay`（还款），移除 `neutral.repay`；系统规则"贷款 / 信用卡还款"（仅支出方向） |
| Q2-A | 银行转入支付宝 / 微信的理财、余额宝、零钱通（同一笔钱两边都有） | **自己账户间转移，两条都保留，都算中性** | 已由"理财申购"规则 + 来源映射实现，测试覆盖 |
| Q2-B | 在支付宝 / 微信里**用银行卡付款消费**（银行"快捷支付" + 平台"支出"，是同一笔消费） | **待确认**。建议：两条都保留，平台那条算支出（明细更细），银行那条标记为"已关联"、不计入统计 | 待定 |
| Q3 | 招行"汇入汇款""银联代付"等无法判断性质的收入 | **靠用户规则** | 不加系统规则，由"从修改中学习"生成用户规则 |

注意：还款算支出后，如果用户同时导入了**信用卡消费明细**，同一笔消费会计算两次（刷卡一次、还款一次）。MVP 暂未接入信用卡账单，接入时需要另行决定（例如信用卡账单导入后，把对应的还款改为中性）。

## 被否决的备选

- **直接沿用各来源自带分类**：微信根本没有消费分类，各家名称也互不兼容。
- **规则支持正则**：安全风险 + 普通用户不会写。
- **所有用户共享一份分类表**：用户没法个性化，一改全改。

## 后果

- 需要 P0-1c 探针：用预置分类 + 系统规则 + 来源映射对真实样本分类，统计各层的覆盖率，用来评估"开箱即用"的效果，也给后续的规则库扩充提供基线。
- P3 的 agent 做自动分类时，产出物仍然是"规则建议"，由用户确认后进入同一套规则体系。
