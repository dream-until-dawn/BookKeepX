# ADR-0003 导入解析模板体系

- 状态：提议中（待确认）
- 日期：2026-09-24

## 背景

需求（负责人 2026-09-24）：
1. 每一种数据来源文件都要有自己的解析模板，后续会持续接入更多银行；
2. 用户只管上传文件，服务端**自动选择**解析模板；
3. 识别不确定时，让用户从候选中选择，或**自定义解析模板**。

P0-1 探针是"每个来源写一个适配器"的方式。它能验证格式，但每接一家银行就要写一份代码，而且用户自定义模板无法复用这条路。

## 决策

### 1. 模板 = 声明式配置（数据），引擎 = 通用代码

解析逻辑拆成两部分：
- **解析引擎**（代码，只有一套）：负责读取文件、定位表头、映射列、转换金额和时间、判定方向、过滤状态、自校验；
- **解析模板**（JSON 数据，每个来源一份）：描述"这种文件长什么样、每列是什么意思"。

接入新银行 = **新增一份模板 + 一份样本夹具测试**，正常情况下不用写代码。
只有遇到引擎还不支持的格式特征（例如招行 PDF 的"对手信息折行"），才去扩展**引擎能力**，并在模板里用配置项开启。不为某一家银行写专门的分支代码。

### 2. 模板结构（草案）

```jsonc
{
  "id": "cmb-pdf",                 // 模板标识
  "version": 1,                    // 格式变更时递增；导入批次记录所用 id@version
  "name": "招商银行交易流水（PDF）",
  "fileType": "pdf",               // csv | xlsx | pdf
  "encoding": "auto",              // csv 用：auto | utf-8 | gbk
  "fingerprint": {                 // 识别指纹：用于自动选择模板
    "titleKeywords": ["招商银行交易流水"],   // 表头之前的文字里必须出现的关键词
    "fileNameKeywords": ["招商银行交易流水"] // 可选，仅作加分项；不用正则
  },
  "header": {                      // 表头定位：第一行同时包含全部 required 列名
    "required": ["记账日期", "交易金额", "联机余额", "交易摘要", "对手信息"]
  },
  "columns": {                     // 字段 → 列名（可给多个别名，兼容改版）
    "occurredAt": ["记账日期"],
    "amount": ["交易金额"],
    "balance": ["联机余额"],
    "description": ["交易摘要"],
    "counterparty": ["对手信息"],
    "currency": ["货币"]
  },
  "amount": { "mode": "signed" },  // signed：带符号单列 | directionColumn：金额 + 收/支 列 | split：收入列 / 支出列分开
  "direction": {                   // mode=directionColumn 时：取值 → 方向
    "column": "收/支",
    "map": { "收入": "income", "支出": "expense", "不计收支": "neutral", "/": "neutral" }
  },
  "status": { "column": "交易状态", "skip": ["交易关闭"] },
  "time": { "format": "yyyy-MM-dd", "timezone": "Asia/Shanghai" },
  "nullTokens": ["/", ""],
  "verify": {                      // 自校验方式，可多选
    "balanceChain": true,
    "summary": null                // 或 { "total": "共{n}笔记录", "labels": { "expense": "支出" }, "countIncludesSkipped": true }
  },
  "preambleFields": { "holderName": "名：{v}" }, // 从说明文字提取户主姓名（用于识别"转给自己"）
  "pdf": { "wrapTolerance": 12 }   // 仅 PDF：列位置由表头列名的 x 坐标动态确定，不写死
}
```

### 3. 自动选择模板（识别）

对上传的文件，逐个候选模板打分（0~1）：

| 维度 | 说明 | 权重（初值，探针后调整） |
|---|---|---|
| 文件类型 | 不匹配直接淘汰 | 淘汰条件 |
| 指纹关键词 | 表头之前的文字命中 titleKeywords | 0.3 |
| 表头覆盖 | 找到包含全部 required 列名的表头行 | 0.4 |
| 试解析 | 用该模板解析前 N 行，成功率 | 0.3 |
| 文件名 | 命中 fileNameKeywords | 加分项 |

判定规则：
- 最高分 ≥ 0.9，且比第二名高出 ≥ 0.2 → **自动选用**，并在预览页显示"已识别为：xxx"，用户可以改选；
- 有候选但达不到上面的条件 → 返回**候选列表**（按分数排序），让用户选；
- 没有任何候选达到 0.4 → 进入**自定义模板**流程。

自动选用后，自校验（汇总比对 / 余额链）仍然是最终门槛。校验没通过，即使分数很高也不入库。

### 4. 模板的来源与存储

| 类型 | 存放位置 | 谁维护 | 能力 |
|---|---|---|---|
| 内置模板 | 代码仓库 `packages/core/importers/templates/*.json`，随版本发布 | 开发者 | 全部配置项 |
| 用户自定义模板 | 数据库 `import_templates` 表（`definition jsonb`），按用户隔离 | 用户在页面上配置 | 同一套 JSON 结构，**只能是数据、不能执行代码** |

自定义模板的流程：上传 → 识别失败 → 前端展示文件前若干行 → 用户点选表头行，把每一列拖到对应字段（时间 / 金额 / 收支 / 对方 / 说明…）→ 预览解析结果 → 保存为模板。下次上传同类文件时，它会作为候选模板参与识别打分。

新增数据表：

| 表 | 关键字段 |
|---|---|
| `import_templates` | id, user_id, name, file_type, version, definition(jsonb), created_at, updated_at |
| `import_batches`（已有，新增字段） | template_id, template_version, detect_score |

### 5. 模板本身的校验

- 模板 JSON 用 zod schema 校验（放在 packages/contracts），格式不合法的模板拒绝保存 / 加载；
- 每份内置模板必须配一份脱敏样本夹具，外加正向测试（解析 + 自校验通过）和反向测试（喂给其他模板时不被选中）；
- CI 跑"识别矩阵"：每份样本 × 每个模板打分，断言只有目标模板被自动选中。**这条测试防止新模板误抢别家的文件。**

## 被否决的备选

- **每个来源写一个代码适配器（P0-1 的做法）**：接入成本高，用户无法自定义，而且内置模板和自定义模板会变成两套机制。
- **模板中允许写脚本（JS 表达式）**：灵活，但用户自定义模板会变成服务端代码执行入口，安全风险不可接受。确实需要的能力，一律做成引擎的配置项。
- **用大模型识别表格结构**：放到 P3。届时可以由 agent **生成模板 JSON** 供用户确认，产物仍然是声明式模板，不改变本体系。

## 后果

- ✅ P0-1b 已验证（[结论](../probes/p0-1bc-templates-and-categories.md)）：通用引擎 + 3 份模板与专用适配器逐笔一致，自动识别全部选对，无关文件不误选。
- 实测修订：模板中一律不用正则，改为占位符 / 关键词；模板 schema 启用严格模式。
- 引擎能力会随着接入的银行增多而增长，每新增一项能力都要写进本 ADR 的模板结构说明。
