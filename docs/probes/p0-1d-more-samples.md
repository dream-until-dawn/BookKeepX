# P0-1d 探针结论：多份历史样本验证

- 日期：2026-09-24
- 分支：`probe/legacy-formats`
- 样本：负责人新增 33 份历史导出（微信 2021–2025、支付宝 2021–2025），加上原有 3 份，共 36 份
- 负责人决定：**不专门兼容旧版格式**（用户使用本软件时导出的都是新版格式）

## 1. 结果总览

| 类别 | 文件数 | 结果 |
|---|---|---|
| 新版格式：微信 xlsx（2025 起）、支付宝 csv（2022 起）、招行 PDF | 9 份，约 2,470 笔 | ✅ 全部自动识别到正确模板，自校验全部通过 |
| 旧版格式：微信 csv（2021–2024） | 24 份 | 进入"自定义模板"流程，**不会被误用模板导入** |
| 被 Excel 另存过的支付宝 csv（2021） | 1 份 | 只列为候选（0.7 分）让用户选，不自动导入 |

旧版格式虽然不兼容，但系统的行为是正确的：认不出就交给用户处理，不会用错模板静默导入。

## 2. 修正：支付宝汇总口径

P0-1 基于单份样本推测"交易关闭的记录计入笔数、不计入金额"。多份样本**推翻了这个推测**：

| 文件 | 旧推测 | 新推测 |
|---|---|---|
| 2022 | ✓ | ✓ |
| 2023 | ✓ | ✓ |
| 2024 | ✗ 支出差 2.89 元 | ✓ |
| 2025.06 | ✗ 支出差 22.70 元，中性差 4.4 万元 | ✓ |
| 2026.09 | ✓ | ✓ |

**新推测（5/5 吻合）**：全部记录（含"交易关闭"）都计入笔数和金额；"退款成功"（记为不计收支）的金额从**支出**汇总中扣除。
P0-1 的那份样本恰好同时有 0.09 元的交易关闭和 0.09 元的退款，两种推测都成立，所以当时无法区分。

教训：**单份样本得出的口径结论不可靠**。测试中已加入能区分两种推测的合成用例：按旧推测写的汇总必须报错。

## 3. 其他发现

- **0 元交易**（全额优惠商品、医保全额支付，状态"支付成功"）：模板新增 `zeroAmount: skip`，跳过并注明原因，仍计入笔数。
- **被 Excel 另存过的文件**：时间变成 `2021/12/31 8:54`（丢了秒），说明行被补满逗号。用户手里被 Excel 改过的账单并不少见。按负责人决定不兼容，识别阶段会给出候选，引导用户重新从 App 导出。
- **旧版微信 csv**：列与新版 xlsx 相同，UTF-8 带 BOM，金额为 `¥11.00` 字符串。如果以后需要支持，只要加一份模板，不用改引擎。

## 4. 分类覆盖率（更多数据）

按时间顺序模拟"从修改中学习"：前面账单中纠正过的交易对方，在后面的账单中自动命中。

| 来源 | 期间 | 笔数 | 系统规则 + 来源映射覆盖后仍需用户处理 |
|---|---|---|---|
| 支付宝 | 2022 → 2026 | 1,820 | 每期 0%–10%，大多在 3% 以下 |
| 微信 | 2025 Q1 | 242 | 28% |
| 微信 | 2025 Q2 | 274 | 21%（上季度的纠正覆盖了 43 笔） |
| 微信 | 2026.08 | 56 | 46%（与 2025 相隔一年多，几乎没有复用） |

结论：支付宝几乎开箱即用；**微信是薄弱环节**（没有分类字段，小商户扫码居多）。短期靠扩充系统关键词和用户规则，长期适合交给 P3 的 agent 生成规则建议。
