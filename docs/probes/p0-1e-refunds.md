# P0-1e 探针结论：退款关联与冲减支出

- 日期：2026-09-24
- 分支：`probe/refund-offset`
- 负责人决定：**退款冲减支出（方案 B）**，见 [ADR-0004 第 6 节](../adr/0004-categories-and-rules.md)
- 结论：✅ 全部 35 笔真实退款都关联到原消费；**支付宝按方案 B 算出的净支出与支付宝官方汇总分毫不差**，说明方案 B 与平台口径一致

## 1. 两个平台的退款形态完全不同

| | 支付宝 | 微信 |
|---|---|---|
| 退款记录 | 单独一条"不计收支 / 退款成功" | 单独一条**收入**，交易类型为"xxx-退款" |
| 原消费的变化 | 全额退款后状态变为**"交易关闭"** | 状态变为"已退款(￥x)"或"已全额退款" |
| 关联依据 | 退款单号 = `原订单号` + `_` 或 `*` + … → **精确** | 单号无关联 → 按对方 + 状态 + 金额，**启发式** |

## 2. 关联规则

**支付宝（externalIdPrefix）**：取退款单号第一个分隔符前的部分，找同单号的支出。
**微信（counterparty）**：
1. 同交易对方、状态含"退款"、剩余可退金额足够，取时间最近的；
2. 兜底：对方名称对不上时（实测"京东" vs "京东商城平台商户"；被退回的转账，退款行对方为空），找"已全额退款且金额相同"或状态写明"(￥该金额)"、且**早于退款**的支出。

两种方式都**禁止超额冲减**：同一原消费被多次部分退款时累计计算，超出的那笔不关联，交给用户确认。

## 3. 实测发现

1. **支付宝"交易关闭"并不都是"没发生"**：全额退款后原消费会变成交易关闭。之前把它们一律跳过，退款就没有东西可冲减。→ 有退款关联的交易关闭**恢复入账**，与退款抵消（两条都保留，净额 0）；没有退款的交易关闭仍然跳过。
2. **微信把退款记成收入**：2025 年第 2 季度有 2,147 元退款被计入收入。方案 B 同时纠正了收入和支出。
3. **被退回的转账**（对方未收款，24 小时后退回）也走退款流程，同样能正确抵消。

## 5. 统计口径

- 退款记在**退款自己的发生时间**，冲减**原消费所在的分类**；
- 找不到原消费的退款（例如原消费在更早、尚未导入的账单里）冲减"其他支出"，并在导入预览中标记"待确认"；
- 正式实现时，跨文件的关联在服务端完成：按单号或对方在**数据库已有流水**中查找原消费。
