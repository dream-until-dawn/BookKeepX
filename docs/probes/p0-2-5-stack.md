## P0-2 数据库链路 ✅

| 验证项 | 结果 |
|---|---|
| drizzle-kit 由 schema 生成迁移 SQL | ✅ SQL 可读、可审阅（约束、外键、索引均按预期生成） |
| 迁移执行 + 重复执行幂等 | ✅ |
| bigint 金额往返（9e12 分、2^53−1） | ✅ 读回为 JS number 且精确 |
| 超出安全整数 / 金额 ≤0 / 非法方向 / 非退款指向原消费 / 退款指向不存在记录 | ✅ 均被数据库拒绝，测试断言**具体错误码和约束名** |
| 按北京时间切月（1 月 31 日 23:30 与 2 月 1 日 00:30 分属两个月） | ✅；对照：按 UTC 切会错归到同一个月 |
| 统计口径：中性不计、跨来源重复不计、软删除不计、退款冲减支出且不计收入 | ✅ 一条 SQL 算完 |
| 分类净支出：退款冲减到原消费的分类，找不到原消费的冲减"其他支出" | ✅ |
| 多用户隔离 | ✅ |

**发现**
1. **手写 SQL 的聚合结果（SUM）是字符串**：postgres.js 默认把 int8 / numeric 返回为字符串，Drizzle 只转换声明了 `mode:'number'` 的列。→ 统一经 `toSafeInt` 转换，超出安全范围时抛错，不会静默丢精度。
2. **只有 `refund_of_id` 不够**：找不到原消费的退款无法和普通记录区分。→ 新增 `is_refund` 标记，并加约束"只有退款才能指向原消费"。
3. 数据库层面加 `amount_cents <= 2^53−1` 约束，与应用层的安全整数检查形成双保险。

## P0-5 图表性能 ✅

**浏览器实测**（生产构建，1 年 / 3,000 笔）：前端聚合 1.2 ms；月度柱图 8.5 ms、分类饼图 3.3 ms、每日折线 8.8 ms。

**压力测试**（ECharts 服务端渲染 SVG，5 次取中位数）：

| 数据量 | 前端聚合 | 月度柱图 | 分类饼图 | 每日折线（点数） | 合计 |
|---|---|---|---|---|---|
| 1 年 3,000 笔 | 0.8 ms | 6.4 ms | 4.8 ms | 11.0 ms（365） | 23 ms |
| 3 年 10,000 笔 | 1.5 ms | 6.0 ms | 3.4 ms | 9.6 ms（1,095） | 21 ms |
| 5 年 50,000 笔 | 7.2 ms | 7.5 ms | 3.4 ms | 9.9 ms（1,825） | 28 ms |
| 10 年 200,000 笔 | 29.5 ms | 9.5 ms | 3.2 ms | 14.3 ms（3,650） | 57 ms |

说明：压力测试改用 SSR，是因为浏览器面板被遮挡时页面不绘制（已验证 `requestAnimationFrame` 不触发），无法在浏览器里测。SSR 走完"配置 → 布局 → 生成图形"全流程，不含 Canvas 像素绘制。

**结论**
- 渲染开销取决于**聚合后的点数**，而不是流水笔数；10 年按天也只有 3,650 个点，不构成瓶颈。
- 聚合随笔数线性增长，并且把原始流水传给前端本身就有传输成本 → **统计一律在服务端 SQL 聚合**，前端只拿聚合结果（与架构文档一致）。
- **ECharts 必须按需引入**：整体引入打包 1.34 MB（gzip 436 KB），按需引入 812 KB（gzip 266 KB，其中大部分是 React）。正式项目中再把统计页拆成单独的代码块，进一步减小首屏体积。
